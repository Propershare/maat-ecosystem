Why software factories fail — Dexter Horthy breakdown

Source: David Ondrej Podcast, Aug 7 2026 — "Ex-NASA dev reveals his Agentic Engineering Workflow" Guest: Dexter Horthy — coined "context engineering", creator of HumanLayer, 12 Factor Agents Companion post: "Why Software Factories Fail" — hlyr.dev/wsff-gh Compiled by: Tehuti Lab / Imhotep — August 8, 2026

Why this matters to Tehuti Lab

This isn't abstract. You're running multiple agentic systems right now — MAAT legal AI with Jarvis mode and UPL Guard, the Alpaca options trading agent doing exhaustive config searches, the Maat-runtime TypeScript stack, MaatRAG with pgvector. Part 1: The agentic software factory — what changed and what didn't

The pre-AI loop (2022 software factory)

CEO/Vision + Product Managers + Engineers → stuff to do → person builds the thing → Pull Request → CI/CD checks, unit testing, static scanning, security checks → human tests + human reviews → rollout/deployment → PROD → MONITORING → incidents/complaints/feature requests → back to stuff to do.

Key reality: building took hours/days. Reviewing took hours/days. We invested in meetings and alignment upfront to save review time on the back end.

The post-AI loop (agent builds the thing)

First substitution: replace "person builds the thing" with "agent builds the thing."

  • fast now Building drops from hours/days to minutes or hours
  • still slow Review STILL takes hours or days
  • A human still has to read the code and test the change
Review is now the bottleneck.

Speeding up review (but not eliminating it)

Next steps most teams take: agentic code review (throw Codex and Opus at it, fix what they find), agentic regression testing (browser testing, computer use), better CI/CD checks, linters, complexity monitoring.

This raises the floor. It catches the small stuff. But the hard judgment calls — "is this going to slow us down in a month?" — still require a human who understands the codebase.

Routing feedback into the factory

The most mature version: user complaints, feature requests, and monitoring incidents get triaged directly into the agent queue. An incident at 3 AM doesn't wake you up to an alert — it wakes you up to a pull request.

Dex is already doing this: GLM 5.2 reviews every uptime incident for Deep API. Agent determines if it's the provider's fault or theirs. If theirs: here's the fix. If the provider: here's a draft message for Discord. Running on Render.com + cron jobs on Vercel + GitHub Actions.

Part 2: The "lights-off" factory — why it failed

The experiment (July 2025)

Dex's team tried running a fully autonomous factory: agents build everything, reviewed plans and tickets but NOT code, collaboration on what went into the to-do list, but zero code reading. All trust placed in automated testing, code review agents, CI/CD.

What happened

They hit a bug the agents couldn't solve. Multiple frontier models in council couldn't diagnose it. They kept "thinking it's something that it's not" and shipping fixes that didn't fix it.

  • Weeks spent reading through sloppy code they hadn't looked at in months
  • Desktop app was buggy, users were angry
  • Complete loss of codebase understanding made debugging exponentially harder
The odds of hitting a bug you can't solve if you stop reading code are much higher than the odds that models will get smart enough to solve it before it happens.

This is not a temporary limitation. It's structural, rooted in how models are trained.

The correction: stay in the loop

Instead of lights-off, the right model is the agent educating YOU: agent quizzes you on the current state of the codebase, HTML visualizations of how the new implementation changes things, multiple choice questions with mermaid diagrams, intentionally slowing down when you start to lose grip.

The word isn't "code" — it's "logic." You need to understand the logic: what does onboarding look like? What happens when someone cancels? What fires when this endpoint is called?

Part 3: Why coding agents write slop — the RL problem

How models get better at coding

The reinforcement learning loop:

  1. Generate agent traces to solve a problem (e.g. fix my tests)
  2. Score the traces based on criteria (verifier)
  3. Update model weights — good traces more likely, bad traces less likely
  4. Repeat millions of times over weeks/months

How benchmarks grade (SWE-bench Multilingual)

Bug report + codebase checked out to pre-fix SHA → agent tries to solve it → produces a patch → graded in sandbox (agent never sees this): throw away agent's test edits, apply the golden test patch → did it fix the new problem? (FAIL_TO_PASS) + did it break anything else? (PASS_TO_PASS) → fixed it + broke nothing = 1, anything else = 0

The critical gap: there is no penalty for bad design.

If the model solves the problem with unnecessary try-catches wrapping everything, lazy type casts, or 10x more code than needed — it still gets a 1.

Why quality can't be verified during RL

Running the tests gets you a clean pass or fail in seconds. That's why RL can run millions of loops. But the cost function of bad architecture is measured in weeks and months.
  • A bad decision now leads to a bug/incident weeks later due to accumulated spaghetti
  • There is no way to backpropagate this signal during a training run
  • There is no fast oracle for maintainability
  • If the model could tell good code from bad code, it would write good code in the first place

Concrete slop patterns

Try-catches that do nothing:

function getUserConfig(jsonString: string) {
    try {
        const config = JSON.parse(jsonString);
        return config;
    } catch (error) {
        console.log("Failed to parse user config JSON");
        return undefined;
    }
}

Lazy type casts that defeat the type system:

function updateProfile(userData: { name: string }) {
    try {
        const customData = userData as unknown as any;
        customData.legacyId = 999;
        return customData;
    }
}

These patterns emerge because the model is optimizing for "make tests pass" not "write maintainable code."

The missing benchmark

Software is "discovering problems as you go." Every benchmark gives the model the whole problem up front. No benchmark feeds the model 5 features in a row and measures whether the codebase stays easy to change.

Part 4: The frontier is getting better, slowly

SWE-Marathon (Abundant AI) — ~400-hour tasks like "clone all of Excel, every feature." Compound reward channel instead of single pass/fail.

DeepSWE (Datacurve) — big tasks on OSS repos that were never actually built in the real world. By construction, can't be in the training set.

Frontier Code (Cognition) — most interesting: multi-PR tasks, LLM judge model (does the solution functionally match the golden solution even if shaped differently?), LLM quality judge (given code quality rules, did the patch follow them?), mutation testing (remove the model's patch, run the model's tests against pre-patch code — if the tests DON'T fail, the model wrote tests that test nothing).

The hype is outrunning the discipline.

Part 5: The 4-stage program design system

Each stage is context-cheap (small token count, high model intelligence) and front-loads the decisions that are expensive to change later.

Stage 1 Product — what are we building and why?

Before any code or architecture: what user problem are we trying to solve? How do we measure success? Write the blog post BEFORE you build the feature (Amazon method). HTML mockups of what the user will see. No tech, no databases, no schemas — just what does the user experience?

If you can define a measurable output, the agent will move mountains for you. Agent can A/B test three approaches, check the data daily, pick the winner. Models never call you out: "you've been working on this for days with zero progress and zero users."

Stage 2 System architecture — how services fit together

How servicesnes. High-level design that the PR reviewer would want to see BEFORE the code. Most builders are comfortable here. This is where the majority stop.

Stage 3 Program design — the layer most people skip

The thing that I think most people skip is actually what I call program design — before you let the agent go cook, there are decisions that it's going to make that you might not like.

What this looks like: where do the files go? What does the call stack look like? Define the types and method signatures (NOT the implementation). What will the tests look like?

// Define types and signatures, NOT implementation
interface ContentChunk {
  id: string;
  source_id: string;
  text: string;
  embedding: number[];
  metadata: Record<string, unknown>;
}

function chunkDocument(doc: Document, strategy: ChunkStrategy): ContentChunk[];
function embedChunks(chunks: ContentChunk[], model: EmbeddingModel): Promise<ContentChunk[]>;
function similaritySearch(query: string, topK: number): Promise<ContentChunk[]>;

Once the model has written thousands of lines, it's harder to change direction. You're deep in a context window, biased by what the model already chose. These design sessions are very token-efficient — high intelligence per token.

Dylan Mroy (Cloudflare): plans end with "here's what the tests will look like" and "here's what the call stack will look like."

Victor Talin (inverse): after the model runs, ask "which choices did you make that you're not confident of?" — Dex's approach does this BEFORE the model runs, when it's cheaper to change.

Stage 4 Vertical slices — build end-to-end first

Models build horizontally by default: all DB first (phase 1, 200 loc) → all services (phase 2, 200 loc) → all API + wire (phase 3, 400 loc) → all frontend (phase 4, 400 loc) = 1200 LoC total with nothing testable until the end.

The vertical approach:

  1. Build a mock API endpoint → test it
  2. Stub out the front end → test it
  3. Wire the front end to the mock → test it
  4. Do the migration → test it
  5. Add business logic → test it
  6. Add error handling → test it
Get it working end-to-end first, then go add logic, then go add business cases.

This is how experienced engineers built software before AI. Hello world → change it until it looks like what you want → push boundaries as you go. You can test at each step, cheaper to resteer early when the code is small.

Part 6: Context engineering — the physics of it

The core principle (12 Factor Agents, March/April 2025)

Own your context window.

Everything you do with LLMs is tokens in, tokens out. The only way to get better results is to put the RIGHT tokens in. Not more — right.

Three rules for context windows:

  1. No wrong information — anything incorrect degrades everything
  2. No missing information — the model can't use what it doesn't have
  3. As small as possible within those constraints

XML is more token-efficient than JSON for context. This matters at scale.

The dumb zone

At roughly 50-60% of context window capacity, model performance starts degrading. The metaphor: a student taking an exam who realizes they have 5 minutes left and starts rushing. Observed behaviors: "context anxiety," cutting corners, scrambling, giving up. Opus 4.5 and Sonnet 4.5 were particularly prone.

The fix: when you hit the dumb zone, compact everything into a document, start a new session from that document. With better models you can push further (200-300k tokens), but the principle holds.

This is training wheels. After ~70 hours of talking to Claude per week for 3 weeks, you develop intuition for when the session is off the rails.

Context in the codebase

Put as much as possible into the file system so the model can access it natively (read, write, edit, grep, bash):

  • /doc/ADR/ — Architecture Decision Records. "We're launching pricing this way." "We never change the API schema; if there's a massive change, ship v2."
  • /doc/external/ — What environment variables exist (not values). Payment processor setup. Which emails for testing. Where customers contact you.

Why files beat MCP servers and instructions: instructions about HOW to get context waste attention tokens while the model is trying to do work. Deterministic context injection is free — a hook that pulls the last 10 Sentry issues at session start costs CPU cycles, not inference. Save inference for reasoning through complex problems.

The signal-to-noise expertise curve

Beginner: "fix this" (no context, no logs, no screenshot)

Midwit: spends 30 minutes writing the perfect prompt

Expert: "It's in that file. Read it and fix it." (one screenshot)

Steering vs context

Two separate concerns: context engineering (what information goes into the window) vs steering/prompting (how much you prescribe the solution). Telling the model exactly how you want it done hits your target precisely. NOT telling it opens a broader probability space — might be terrible, might find a better approach you never considered.

Part 7: Bottleneck theory — The Goal (Eli Goldratt)

From "The Goal" (1970s book): factory has multiple stations, each with different processing times. MBAs optimize utilization of individual stations. This creates work-in-progress pileups in front of the bottleneck. Optimizing a non-bottleneck station does NOT improve total throughput.

Stop playing with your coding agents and get back to work.

The trap: it's fun to build the thing that builds the thing. Token-maxing culture. Building fancy multi-agent routing and delegation. Meanwhile: production is down, or you have zero customers.

There are inefficiencies that are not bottlenecks. You may see things that make your skin crawl. And if you care about entrepreneurship, the most important skill is: zoom out, ask yourself, is this a bottleneck? Can I just hold my nose and focus on the thing that really matters?

The Starcraft analogy

Running a software factory is like Starcraft: constantly making hundreds of decisions with incomplete information. You only know what you've seen. Stacking probabilities. Knowing what you've seen, making bets, calculating expected value.

We are all gambling. We are all gambling all day every day trying to figure out what's the highest expected value.

Part 8: When to vibe code vs. when to engineer

Vibe code when: pre-product-market-fit, figuring out what's worth building, putting different things in front of customers to see what they'll pay for, solo or very small team exploring.

Engineer when: you know what you're building, people are paying for it, you need it around in 6 months, maintainability matters (5+ engineers), regulated industries where bugs = fines (fintech, legal).

Still try to architect it in a way that scales. Still try to keep your grip on the codebase. But ultimately, if you have zero customers, first figure out if you're building a thing that's even worth building.

Part 9: Key quotes worth keeping

If the model knew what good code looked like, then it would be able to write it in the first place. We're all using the same freaking models.
How can you spend a little bit of time upfront to increase the odds that the thing that comes out is not going to need a lot of fixes and changes before you can merge it?
I can easily find myself working for 3 hours on some problem, then I go on a long walk and I'm like, man, this doesn't matter to the business at all. And that was MY dumb zone.
You're not actually competing against Anthropic. You're competing against a product manager at Anthropic. A small founder who really gives a shit can out-execute most teams inside a giant enterprise.
I like to build things in the vein of they're aligned with the world I want to live in.

Part 10: Application to Tehuti Lab systems

MAAT legal AI (Jarvis mode)

Your system already demonstrates several of Dex's principles:

  • Program design discipline: UPL Guard as a governance layer, Ma'at Audit scoring (TR, JU, HA, BA, OR, RE, PR, RI, CO), structured matter management
  • Vertical slicing naturally: each matter is a vertical slice — case loaded → context retrieved → RAG inject → drafts → attorney review
  • Context engineering: quick access panel for statutes, clerk systems, CourtListener — deterministic context injection, not wasting inference
  • Human in the loop by design: "ALL WORK PRODUCT → ATTORNEY REVIEW" — UPL Guard IS the "don't go lights-off" principle applied to legal

Where Dex's lessons apply: as you scale matters, the bottleneck shifts from "can the agent draft" to "can the attorney review fast enough." Document ADRs for citation patterns, RAG strategies, audit thresholds. Keep Ma'at Audit scoring deterministic.

Trading agent (Alpaca options)

Your exhaustive search (533 configurations, zero positive out-of-sample) is the RIGHT application of Dex's measurable-output principle: you defined a measurable goal, the agent searched exhaustively, the result was definitive. That's valuable — it prevents deploying a losing strategy.

Where Dex's lessons apply: vertical slicing for new strategies (get ONE signal end-to-end first). The bottleneck question — if 533 configs produce nothing, more configs won't help; the bottleneck is the signal hypothesis itself. Code maintainability in risk management is where "weeks later" bugs would be catastrophic.

Information department / RAG system (current build)

This is where the program design methodology applies most directly RIGHT NOW:

  • Stage 1 What does the content creator (you) need from the system? How do you measure success?
  • Stage 2 How do OCR, PostgreSQL, pgai, Ollama, and the content pipeline fit together across three machines?
  • Stage 3 Before letting agents build the ingestion pipeline — define table schemas, chunking strategy, types for ContentPiece, Chunk, SearchResult
  • Stage 4 Get ONE book chapter → OCR → clean text → stored in Postgres → retrievable by semantic search. Test it. THEN add metadata extraction, multi-category routing, automated classification.

Summary: the workflow in one page

1. PRODUCT DESIGN (no code)
   What problem? How do we measure? What does the user see?
   Write the blog post before building the feature.

2. SYSTEM ARCHITECTURE
   How services fit. Endpoints. Tables. Query outlines.
   This is what the reviewer would want to see first.

3. PROGRAM DESIGN (most people skip this)
   Call stack. File placement. Types and method signatures.
   What the tests will look like. NO implementation yet.
   → This is where you bring your hard-earned intuition
     to leverage.

4. VERTICAL SLICES
   Build end-to-end first with stubs/mocks.
   Test at each step. Add logic incrementally.
   → Cheaper to resteer early than to rewrite at the end.

5. BUILD (let the agent cook)
   The agent is now working within your constraints.
   It solves problems well. It writes slop if you let it.

6. REVIEW (the bottleneck)
   You read the code. You understand the logic.
   Agent code review catches the small stuff.
   Your intuition catches the design problems.
